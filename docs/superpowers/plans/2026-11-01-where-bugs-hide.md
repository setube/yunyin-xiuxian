## 一、读档不设界（13 条，占一半）

一条坏档能走完全程：字段存在、类型是对象、`sanitize()` 也在，
唯独没人检查它的**值域**。这是本仓库最高发的缺陷形态。

细分四种：

1. **容量**：行囊 `BAG_CAPACITY`、灵脉总量、道童槽位、构筑列表 `MAX_LOADOUTS`
   ——撑爆后永久卡死（`recruit` 恒返 full、`applyLoadout` 越界）
2. **条数**：单件词条 `EQUIP_AFFIX_HARD_CAP`、辅修 `SUB_GONGFA_SLOT_HARD_CAP`
3. **长度**：道号与构筑名 `NAME_MAX_LENGTH`
4. **量级**：GNum 指数无上界 → 界面印出 `1.00e1000000000`
   （`saveShape.asBoundedGNum` 就是为这个加的；`SAVE_GNUM_MAX_EXP = 999`）

**最隐蔽的一档**是嵌套对象：`world.rules` 只判了「是不是对象」，
内部 `playerStartHpPct: Infinity` 经 `mulN` 变 0，玩家一进战斗即判负。
凡人界与虚界是同一个 `resolveCombat` 的两个入口，各漏一次。

**守卫**：`src/utils/nestedShapeGuard.spec.ts`（只判类型不判字段会红）、
`src/core/tierLandmine.spec.ts`（层级尺）、`src/stores/resources.spec.ts`（指数界）。

## 二、一致性缺口（5 条）

规范存在、同类代码也照做了，但新写的几处没跟。**不会让任何测试变红**，
只能靠专门的一致性扫描发现。

实例：九处互斥选择钮缺 `aria-pressed`、三处展开钮缺 `aria-expanded`、
三处禁用钮缺拒因、`AGENTS.md` 十二个状态词在代码里却无测试引用。

**找法**：拿文档当查询条件反查代码覆盖率。`AGENTS.md` 的
「固定写法」「禁用即给原因」「层级地雷」几节，每条硬性规定都该有一个断言。

注意 `aria-pressed` 是 **toggle** 语义（0~N 个可选中），
`aria-selected` 才是 **selection**（恰一个）——两者混用会误报。

## 三、逻辑边界（5 条）

入参落在没想过的区间：`overReachFactor(1.5)` 令表查不到 → `undefined` 混进成功率；
`exploreEventChance` 负加成 → 离线战斗数虚增；战力星串收到小数 → 产出四个字符。

**共性**：函数对「正常输入」正确，对边界没定义。

## 四、静默失败（2 条）

最难查的一类：不报错、不崩、无日志，只是没生效。

- `useAutoReforge.runAutoReforge` 开头按 `inst` 提前返回,而装备已不在行囊时 `inst` 恒为 undefined
  → 下面「未找到装备」那条提示永远走不到,玩家点了没反应（第 85 行注释记着这段）
- `useGameClock` 在组件外调用 → `onMounted` 被静默忽略，倒计时从此静止

**注意**：`useGameClock` 这类**至今没有防御**，只靠
`src/composables/useGameClock.spec.ts` 守住调用点边界。

## 五、工具误报（2 条）

验证工具自身的规则写错，把正常行为判成缺陷。**误报率高的检查等于给真缺陷发免检通行证。**

- `ui-smoke` 把「有回执的拒绝」（弹 toast 后 return）判成死按钮
- `layout-check` 把可取消的开关组（全不选）判成「没选中态」

两条都是**我自己引入的误报**：前者是判据单一信号，后者是语义搞混。

## 六、注释过期（2 条）

`motivationType` 里「与 worldGen 同构」、道侣服务里的属性键总数。
文档与代码不一致时**以代码为准**，并顺手改掉注释。

## 七、标签与数值脱节（217~218 轮，2 条）

**这一类最难被测试发现**：所有用例都绿。品阶字段在、倍率公式在、
阶梯「不回落」的断言也在 —— 但它只保证不倒退，不保证**拉开了**。

实例（218 轮同时修掉的两族）：

- 法宝伤害族 t19 精品 6.325 → t31 天品 6.485，跨 13 个层级、5 个品阶只强 2.5%
- 灵兽玄品（预算 0.60~0.70）整体弱于灵品（1.00~1.30），神品白泽 1.50 低于仙品应龙 1.60

两者的根因相同：**高阶基线被写低，靠品阶倍率补偿，两条相抵后净增长归零**。
法宝那条更隐蔽 —— 数据里 `mult: 2.86` 看着是个大数，乘上 2.236 的品阶倍率才 6.4，
而低阶那件 `mult: 5.0` × 1.265 恰好也是 6.3。

**守卫**：`artifactLadder.spec` 的「最深那件至少是最浅那件的 N 倍」、
`petLadder.spec` 的「相邻品阶区间不重叠」。这两条都不是「不回落」，
而是「拉开了多少」—— 写阶梯守卫时容易只写前者。

## 八、形制不可辨（218 轮，1 条）

规则对、数值也对，但**玩家看不出来**。九档品阶原先只有三档浓淡（边框与底色的
一个 alpha 值），隔着屏幕分不出天品与神品。

浓淡是连续量，三档已经是极限；可数的线索要靠**形制**：
外发光档位、角饰枚数、名牌描边、神品独有流光（见 `src/ui/qualityAura.ts`）。

**判据**：把「稀有度」想成要能用一句话说清的差异（「神品有三个角，天品两个」），
说不清就说明形制还没拉开。

## 九、少报差额（217 轮，1 条）

提示文案照 `formatGN` 写，而它是四舍五入：差 1.824 印成「灵石尚差 1.8」，
玩家补 1.8 仍然不够。差额提示单独用 `formatGap`（末位一律向上进一）。

**原则**：差额宁可多报不可少报 —— 多报 0.1 只是多补一点，少报 0.024 会让玩家反复试。

## 十、量纲错配（231 轮，1 条）

两个「等效时间」口径各自都对，混进同一个「它值多少」里就错了。

实例：修速丹的等效挂机秒 = **时长 × 速率加成**，与境界无关；
而它要顶替的那一次闭关（修为丹的 `expSecs`）随境界涨了近 1500 倍。
于是境界 0 的聚灵丹与同档修为丹持平（100%），境界 20 的混天丹只剩 **12%** ——
同样花灵草、同样占一个丹方位，炼它不如直接炼修为丹。

**这类缺陷的特殊之处**：公式没错、每味丹单独看也合理，错在**两条曲线没有一起走**。
查法是把同族丹药按境界排成一行，算「它的值 ÷ 同档替代品的值」，
看这个比值是否随境界漂移 —— 单看绝对数值看不出来。

**修法与判据**：拉长高境界修速丹的持续时长（取古时制整档，文案也就能写「一个时辰」），
并加一条守卫：修速丹不得低于同档修为丹的 35%，也不得越过 150%
（修速丹是「边打边修」的副渠道，不该完全顶替闭关丹）。
容差带而不是等号，是因为低境界本就该由短时丹承担。

## 十一、满级让控件消失（235~236 轮，3 条）

代价函数在满级/满重时返回 `null`,而按钮写 `v-if="cost"` —— 于是那颗钮直接不见。
**同一形态连续踩了三次**:装备强化钮、强化面板(整块消失)、法宝炼化钮。

为什么它比「写错文案」严重:

- 玩家看到的只是「强 化」「炼化」凭空不见,既不知道是不是满了,也看不出是不是坏了
- 并排的两颗钮各占一半,一消失整行宽度重置,页面还会跳一下
- 截图才发现:第一版把按钮文案写全成「强化已至上限」,那一格是两字钮,四个字被压成两行

**判据不是「不能出现 v-if」,而是「代价为 null 时仍有一句话」**。
守卫在 `ui/masteryMark.spec`(故障注入:把任一处改回 `v-if="cost"` 即红)。

`GongfaDialog` 曾被我判成「不是缺陷」,理由是「满级时下面本来就走悟道分支」——
**那个判断是错的**(249 轮推翻)。正文里的悟道面板与页脚那颗钮是两件事:

- 页脚「进 修」与「设为主修 / 辅修」并排各占一半,它一消失整行宽度就重置、页面跳一下
- 悟道面板讲的是「满级之后还能干什么」,解释不了「进修钮去哪了」

判据回到同一句:**代价为 null 时仍有一句话**。四处落点现在都在守卫里
(装备强化钮 / 强化面板 / 法宝炼化钮 / 功法进修钮)。

## 查过但不是缺陷（231 轮）

记下来免得下次重查：

- **装备 `fixedMods` 逐阶波动**（0.11~0.63，非单调）：装备的主强度是
  `base × powerScale(tier)`，实测每阶 1.4~4.6 倍、严格单调；
  `fixedMods` 是附加特色，本就按身份设计，横比不是同一量纲
- **天赋各等预算区间重叠**：`budgetOfMods` 是机制复杂度会计，不是强度
  （`talentLadder.spec` 头注释早写明）。四等的真实承诺是「不被支配 / 期望更强 / 各有领地」，
  三条都已有守卫
- **称号没有品阶字段**：29 顶称号只有 `mods`，不参与稀有度排序，不存在倒挂
- **天气随界域递增**：人间界 1.20 → 仙界 1.50 / 0.60 → 混沌海 2.00，正常
- **丹药品阶与其准入境界的分段**：mortal 只 1 味、divine 有 17 味，是内容分布不是强度问题

### 操作没有 toast 的几种合法情况（232~234 轮）

找「点了没回执」时最容易误报的是下面几类。**判据是「玩家能不能当场看出成没成」**，
不是「有没有 toast」：

| 情形 | 实例 | 为什么合法 |
| --- | --- | --- |
| 服务层已报 | `refineEquipment` / `deleteLoadout` / `captureLoadout` | 视图函数只是转调,回执在 core |
| 效果即时可见 | `CreateView.reroll`(灵根重掷)、`EquipNotePanel.applyNote`(备注出现在卡上) | 结果本身就是回执 |
| 同一视野内按钮翻面 | `EquipmentDetailDialog.toggleEquip`(装备 → 卸下,就在旁边) | 下一步动作当场变了 |
| 纯视觉 | `GauntletPanel.skip`(快进战报)、`ui.dismissToast` | 不写游戏状态 |
| 选择即完成 | `MentorDialog` 点卡片拜师(有高亮) | 选中态就是回执 |

**反面则是真缺陷**：`ArtifactPanel` 的祭炼/收回虽也翻按钮文案,但那颗钮在列表下方、
卡片上只有一个「祭」字小标记,玩家看不出「这颗钮刚才做了什么」——
所以它需要 toast。区别在于**回执离操作有多远**,不在于有没有。


## 找 bug 的优先顺序

1. **有明文规范但无断言的地方**（第二节的找法，命中率最高）
2. **刚加过新字段/新入口、但只加了一处的地方**（`world.rules` 就是第二入口漏了）
3. **`sanitize()` 里只判类型不判值的地方**
4. **零 spec 的模块**（本项目里真 bug 多出自此：路由守卫、`CreateView.starting`、
   `useAutoReforge`、`useBondOverview`/`useRegionRows`）
5. 边界入参（小数、负数、0、Infinity、超大 GNum）
6. **「字段在、公式在、测试绿，但玩家感觉不到」的地方**（第七、八、十节）——
   查法是把数值**印成一张表按阶排**，肉眼找平台期；不要靠读代码，
   因为补偿项与基线相乘时，任何一处单看都合理
7. **两条曲线各自都对、但没有一起走的地方**（第十节）——
   算「A 的值 ÷ 同档替代品 B 的值」，看这个比值是否随境界漂移；
   单看绝对数值永远看不出来

## 别做的四件事

- **别把等价重写当修复**：`toNum` 那次两种写法返回值完全一致，
  改动只是去掉了一个隐含前提，commit 里如实写了「不改变行为」
- **别把正常行为当缺陷**：突破失败不退还灵气是**有意设计**
  （`src/data/statNames.ts` 第 65 行注释写明），炼丹后材料变多是主线奖励
- **别留会误报的守卫**：宽松判据会逼后来人给正常代码打补丁。
  判据宁宽勿严 —— 漏报只是少一条提示，误报会破坏工具的可信度
- **别把代码位置当作运行时作用域**：197/205 轮看到 `dimDisabled` 只写在 `measurePage` 里，
  就断言「弹窗里的禁用钮从未被检查过」，还据此写进了 commit。实际 `measurePage` 查的是
  `document`，而弹窗巡逻那步会在弹窗打开的状态下**再跑一次** `measurePage`
  ——整页判据本来就覆盖弹窗。215 轮造了个 `.modal-panel` 实测才确认。
  **结论前先跑一次，别从代码结构推断行为。**

## 十二、首次游玩链路实测（238 轮，0 条）

从零存档走了一遍完整首玩链路，**没有发现缺陷**。记下走法与结论，免得下次重走：

```
欢迎页 → 开始游戏 → 隐私确认(须先勾选同意,否则按钮 disabled) → 传送门 2.5s
→ 建号页(道号 / 灵根 / 逆天改命) → 踏入仙途 → 灵根鉴定 2.2s + 离场 0.4s
→ 首页(六个功能格 + 「第一步:去历练」高亮) → 历练页
```

实测确认健康的地方：

- **隐私确认的前置**：同意钮有 `:disabled="!agreed"`，不勾不让走 —— 这是设计不是 bug
- **传送门与鉴定动画的时长**：2.5s / 2.2s，等待不足会误判成「点了没反应」
- **首页格子初始发灰**：那是 `stagger-in` 入场动画（实测 `opacity` 从 0 到 1），
  截图早于动画结束就会误判成「禁用」
- **「本世之界」显示「此世未成」**：新号凡人界尚未凝成，正常状态词
- **历练页的「静心凝神 / 悟透瓶颈 / 吐纳有序」**：那是顿悟选项池的模板文字，
  不是新号自带的三个 buff

**走查时的两个自坑**（与缺陷无关，但会让结论全错）：

1. 带字距的按钮（`tracking` / 手打空格）`innerText` 是「开 始 游 戏」，
   `getByRole('button', { name: '开始游戏' })` 找不到。要按去空白后的文字匹配
2. 入场动画未跑完就截图，会看到一片灰 —— 判「禁用」前先读 `opacity` 与 `disabled`

## 十三、反震流打首领 3%：查清根因但**没有修**（239 轮）

`softCapAudit` 的矩阵里,反震流对首领常年 0~3%。239 轮查清了根因,**结论是先别动**。

### 根因:atkMult 0.78 是唯一瓶颈

只改这一项,其余不动(每点 200 场实测):

| atkMult | 0.78 | 0.85 | 0.90 | 0.95 | 1.00 |
| --- | --- | --- | --- | --- | --- |
| 首领胜率 | **0.5%** | 9.0% | 24.5% | 39.0% | 59.0% |

机制上也说得通:反击伤害是 `0.5 × (1 + counterDamage)` × 自身攻击,
反震流 `counterDamage 1.5` 仍要乘 `atkMult 0.78`;首领 2600 血 + 自带护盾,
24 回合打满(逼近上限)也磨不掉。**不是惜败,是打不动。**

中间还验证过一条:把 `artifactId` 从缚妖索(削弱敌人攻击 20%)换成任何别的法宝,
首领胜率都会跳到 91%~99% —— 但整体均值同时冲到 87%~96%,越过了「无霸主 ≤88%」的线。
**削弱法宝在这里是压舱石,不是配错。**

### 为什么没修:三条既有约定把可行域夹死了

在同一套约束下穷举 `atkMult × counterRate × counterDamage × damageReduction × executeDamage`,
**符合条件的组合为 0**。三条约束互相冲突:

1. `celestialJudgementInvariant`:`counterRate + counterDamage + damageReduction < 2.6`
   (`modDepth` 把所有非攻防血的正向词条直接相加)。提高 `counterDamage` 就顶到 2.6
2. `buildSim.spec` 的克制关系:锋芒打高爆发 > 反震打高爆发 + 8 个百分点。
   反震的机制(被打就反击)对高爆发**天然有优势**,抬 atkMult 必然同时抬这一格
3. 均值须落在 45%~88%(无废柴也无霸主)

试过的路线与结果:
- 纯抬 `atkMult`:首领 24%,但高爆发 53% > 锋芒 39%,第 2 条破
- 加 `executeDamage`(只伤血未满之敌):能只抬首领,但 `modDepth` 越界,第 1 条破
- 用 `executeDamage` 换掉一部分 `counterDamage`:12 组全部在第 2 条上破

### 真要修的话,得先回答一个问题

**反震流「怕高爆发」这个设定还成立吗?** 它的机制是挨打就反击,对攻击频繁的敌人本该有优势。
原矩阵里那 26% 是被 `atkMult 0.78` 压出来的**假象**,不是机制上的克制。
若确认这条设定该改,修法是先改断言(把「锋芒 > 反震」换成别的区分方式),
再抬 `atkMult` 到 0.9 —— 那是一次设计决策,不是一次 bug 修复,需要拍板。

## 十四、包体实测：健康，只有一处已知浪费（240 轮）

量了一遍首屏,结论是**不必优化**。数据留档,免得下次再花一轮重新量:

| 项 | 实测 |
| --- | --- |
| 首屏直接加载 | `polyfills` + `index` = **121.5 KB gzip** |
| 首屏含 modulepreload(24 个) | 344 KB gzip |
| 主 CSS | 99.5 KB → **29.0 KB gzip** |
| 资源总数 | 161 个 |

24 个预加载里,一个 `player-*.js`(178 KB gzip)就占了 80%;
其余 23 个加起来只有 44 KB。**切分本身没有问题,是那一个块太大。**

### 那一个块为什么大,以及为什么不动

它叫 `player`,但里面装的是 Vue 运行时 + **CryptoJS**(约占该块 84%),
被「依赖 player store 的模块」一起卷进来的,文件名有误导性。

CryptoJS 进首屏是因为 `utils/storage.ts` 也要用 —— 而 Pinia persist 的
`serialize` / `deserialize` **必须同步**(`JSON.parse(readSaveText(raw))` 直接嵌在配置里)。
把 `encryptSave` / `decryptSave` 改成异步会一路牵到启动流程,
换轻量实现则要自己担 AES 的正确性 —— **回归风险远大于 150 KB 的收益**。

真要改,方向是「存档加密换 WebCrypto + 首次读档前 await 一次」,
那是一次基建改造,不是细节打磨。

### 同轮顺带测的两项(都没问题)

- **极端数值不泄漏**:把灵石塞到 `{ m: 9.99, e: 999 }`、灵气 1e18、其余资源全 0,
  逐页扫 12 个路由的 `body.innerText`,`NaN / Infinity / undefined / null` 零命中
- **存档防线**:`storeResilience`(12 例)与 `importCorruption` 全绿;
  `deadExportAudit` 也绿,ALLOWLIST 仍只有 1 条

## 十五、功法顶级五部同形：查了，判定为设计（242 轮）

主修功法里 r6/r9/r14/r18/r20 五部都是 `cultivationSpeed+attackPct+defensePct+maxHpPct`。
看着像「顶级偷懒」，查完**判定不是缺陷**：

- 五部的 **element 各不相同或有意重复**(chaos / wind / thunder / chaos / chaos),
  而 element 不是装饰:`gongfaService` 按它对参悟掉落加权,`linggenAffinity` 按它算灵根亲和
- **神通名与倍率各不相同**(2.8 / 3.0 / 3.4 / 3.8 / 4.0)
- 主修其余 22 部**方向分工很细**(攻击/防御/闪避/吸血/破境/寿元/暴击/斩杀/震慑),
  只有顶级走「综合型」—— 最高阶给全面强化是合理设计

试改过两次都撞墙,记下来免得重试:

1. 道祖本源经改 `armorPen+executeDamage`:满级预算 8.60 → **10.00**,越过单件上限 9
   (`executeDamage` 权重 0.3、`armorPen` 0.18,比 `defensePct`/`maxHpPct` 的 0.25 更贵,
   等值替换必然超)
2. 混元无极经改 `damageReduction`:8.30 → **9.70**,同样越界

`gongfaLadder` 只管预算阶梯(中位数递增、下沿不低于上一档中位数),不管词条组合 ——
所以真要改组合,**先要腾出预算**,那是数值重排不是措辞修复。

## 十六、`budgetOfMods` 不是强度（第 51~52 轮，同一个坑踩了三次）

`budgetOfMods()` 是**机制复杂度会计**，不是强弱。它把所有非攻防血的正向词条按权重相加，
权重反映的是「这条机制有多稀有」，不是「它有多强」：

| 词条 | 权重（约） |
| --- | --- |
| `cultivationSpeed` | 3.3 |
| `maxHpPct` | 5.5 |
| `attackPct` | 5.8 |
| `breakthroughRate` | 10.0 |

于是会出现「预算低的那件其实更强」：

- **称号「元婴大能」0.30 < 「金丹老祖」0.40** —— 元婴大能带的是 `breakthroughRate 0.01`
  （权重 10），机制上更稀有；曾被误判为「后拿的称号更弱」
- **称号「万道之祖」0.40 < 「神王御宇」0.60** —— 终局称号的 `cultivationSpeed 0.08`、
  `breakthroughRate 0.015` 都是全称号最高；预算低只是因为用了 2 条机制而对方用 3 条
- **灵兽**：同品阶内预算横比也曾被当成强度排序

**正确做法**：

1. 判强弱看**逐条词条的绝对值**，以及 `powerScale(tier)`、`realmsScale` 这类真正驱动强度的函数
2. 预算只在**同机制条数**之间横向比才有意义
3. 拿不准就跑战斗模拟（`buildSim` / `softCapAudit`），那才是玩家实际感受到的东西

这条与「标签与数值脱节」是镜像问题：那一类是「标签说强、数值没跟上」，
这一类是「用会计口径去读强弱」。两者都会让人改错东西。

## 十八、怀疑一条曲线之前，先搜有没有审计 spec（第 71~79 轮）

第 77 轮测出：仙界以后**战力每个大境界涨 4.60 倍，坊市物价只涨 1.90 倍**，
累积到 m20 差四个数量级。看着像严重的后期通胀。

第 79 轮找到答案 —— `src/core/economyAudit.spec.ts` 有五条断言把这件事写死了：

| 断言 | 说明 |
| --- | --- |
| 早期 pole:硬瓶颈(比值 <0.7) | 早期本就该紧 |
| **后期 pole:收入过剩(闲置,>10)** | **后期本就该富余** |
| 中期 realm ~10 亦已进入闲置带 | 中期就开始富余 |
| 全程峰值被同一 ceiling 锁死 | 有上限保护 |
| **两极并存被文档化为已知偏离** | **已知并记录在案的设计** |

「早期紧、后期富」是这款放置游戏刻意设计的经济曲线,而且守卫在防止它**恶化**。
我看到的比值正是它的表现,**不是缺陷**。

### 方法论

这个项目对经济、平衡、阶梯有成体系的审计守卫,盲改一条基础曲线的风险极高 ——
`stoneByTier` 一处改动会牵动坊市、悬赏、炼丹、灵脉、投点等全部灵石价格。

**在怀疑某条曲线之前,先做这一步**:

```
grep -rln "<函数名>\|<相关词>" src/core/*.spec.ts
```

有专属审计 spec 就先读它的 `it(...)` 标题 —— 标题通常就是设计意图的浓缩。
读懂了再决定改不改;读不懂就先报告,不要动手。

### 这条已经救回四次误改

1. `budgetOfMods` 当强度用(第 41、51、52 轮)
2. `stoneByTier` 后期低增长当通胀缺陷(第 77 轮)

两次都是「数据看着不对」,查完发现是**刻意的设计**。

## 十九、两个「验证时会骗自己」的操作陷阱（第 80~88 轮）

不是项目缺陷,是我自己踩的,记下来避免重犯。

### 1. 管道会掩盖退出码

```bash
bun run check 2>&1 | tail -2 && git add ... && git commit ...
```

`$?` 取的是 **`tail` 的退出码**(恒为 0),不是 `bun run check` 的。
于是「门槛红着」和「可以提交」串成了一条链,第 80 轮就这么把一份未过门槛的提交推了上去。

**正确写法**:

```bash
bun run check > /tmp/chk.log 2>&1; echo "EXIT=$?"; tail -3 /tmp/chk.log
```

### 2. 被 gitignore 的临时文件不进 `git status`

第 75 轮写的探针 `src/_mp2.spec.ts` 被 `src/_*` 规则忽略,所以 `git status` 一直显示干净 ——
但 `docs-check` 扫的是**文件系统**,它数出 387 个 spec,而 README 写 386,门槛红了。

**判「工作区干净」不能只看 git**,清理探针后要用:

```bash
find src -name "_*.spec.ts"
```

确认没有残留。这条盲区存在了几十轮,直到 `docs-check` 报错才暴露。

### 一句话

**验证门槛看真实退出码,清理临时文件用 `find` 确认。** 两件事都不花时间,
但它们决定了「我以为绿了」和「真的绿了」之间的差距。

## 二十、法宝的 desc 与灵兽的 desc 不是一个层级（第 141~143 轮）

灵兽的 `petLore` 守卫成立:它的 `desc` 覆盖的就是 `mods`。
于是顺理成章想给法宝套同一套判据 —— 拿 `desc` 去对 `active.effect.type`。**这么做是错的。**

第 142 轮探针跑出 8 件未命中,逐条查下来全是词表噪音,没有一处真问题。
原因在数据结构:

| | desc 描述什么 | 由谁对账 |
| --- | --- | --- |
| 灵兽 | 就是它的 `mods` | `petLore` |
| 法宝 | **被动(passive)** | 无人,也无须有 |
| 法宝神通 | 由 `active.desc` 自己对账数值 | `artifactEffects` |

典型例子「周天星盘」:`desc` 写「推演周天,窥探命数」,被动是
`luck + cultivationSpeed + accuracy`(推演 → 气运/命中/修速);神通叫「星辉」,
「每 4 回合引星辉入体,回复 24% 生命」。描述与被动严丝合缝,
拿它去对 `heal` 当然对不上。

**教训**:同名字段在不同表里可能承担不同语义层级。套用守卫前先问一句
「这个字段描述的是哪一层」,否则做出来的是一条满屏误报的检查。

## 二十二、品阶的视觉差异化是到位的(第 193~204 轮)

用户最初的诉求有一半是审美的 ——「有些名称、有些效果应该一看就知道是高级物品,
甚至应该有一些更独特、更好看的 UI 美化效果」。这一类只能靠**看**,不能靠脚本读数。

### 方法

同一屏放几件**同为 0/9 重**的不同品阶物件,截图对比。
关键是**都取零重** —— 否则「满重」会和「品阶」两个变量混在一起(第 194 轮就踩过)。

### 结论:一套五档的色彩光谱

| 品阶 | 卡片边框 / 四角角饰 / 柔光晕 / 右上印记 | 观感 |
| --- | --- | --- |
| 凡品 | 全无 | 朴素 |
| 精品 | 全无,字色转灰 | 朴素 |
| 天品 | **金色**一整套 + 金线品阶标签 | 明亮 |
| 仙品 | **青碧**一整套 | 清冷 |
| 神品 | **朱红**一整套 | 浓烈 |

- **品阶越高,色彩越浓烈、越独特** —— 凡品与精品无任何装饰,天/仙/神各有一套专属色
- **三类系统配色完全一致**:

  | 品阶 | 法宝 | 灵兽 | 装备 |
  | --- | --- | --- | --- |
  | 神品 | 朱红 | 朱红 | 朱红 |
  | 仙品 | 青碧 | — | 青碧 |
  | 天品 | 金 | 金 | — |
  | 凡 / 精 | 无装饰 | 无装饰 | 无装饰 |

  玩家学会一次,三处通用
- 五项视觉特征**全部由品阶触发,与祭炼重数无关** —— 零重的神品已足够醒目,不必练满。
  唯一随重数变的是祭炼进度条的填充

### 两次差点误判,都是「只看到光谱的一段」

1. 第 194 轮拿「天品满重」对「凡品零重」,分不清金色边框来自品阶还是满重 ——
   改成两件都零重才隔离出变量
2. 第 200 轮看到「天品法宝金、神品灵兽红」,断言两套体系不统一;第 202 轮查计数
   才发现法宝也有仙品神品,第 204 轮截图看到**神品法宝正是朱红** —— 系统其实是统一的

**只凭部分样本推断整体,很容易得出反向结论。**

### 方法教训

前一百多轮验的都是「数据对不对、脚本报不报错」,从未打开界面看图。
而 `layout-check` 能测「有没有横向溢出」,测不出「看起来贵不贵」。
**正确性检查和观感检查是两条互不替代的线**,这次是第一次走后者。

## 二十三、印面的对比度:两套主题各坏一半(第 247 轮)

`.seal-face` 是 2026-10-06 为「夜主题黑字顶红方」加的,AGENTS.md 也明文写了
「朱/金/靛/紫印章上的印面文字用 `.seal-face`,不要用 `text-paper`」。
但**没有断言**,于是十处印面仍在用 `text-paper`,功法门类 tab 的激活态也是。

### 形态:两套主题各坏一半,谁都不全坏

| 写法 | 日主题 | 夜主题 |
| --- | --- | --- |
| `text-paper` + 彩色底 | 5.32 ✓ | **3.83 ✗**(paper 被翻成近黑) |
| `text-paper` + 彩色底 `/85` | **4.17 ✗**(混纸变淡) | **3.13 ✗** |
| `.seal-face` + 彩色底 `/85` | **4.17 ✗** | 5.31 ✓(深朱兜住) |

**这就是它躲了四十多轮的原因**:只开夜主题看不到第二个,只开日主题看不到第一个。
两种检查各自都能给出「没问题」的结论。

### 修法与判据

- 十处印面改 `.seal-face`,底色一律取整色(去掉 `/85`、`/90`)
- 印面挂**整块**而不是挂到里面的字上:`.seal-face` 带背景,挂子节点会在印面上再压几块深朱
  —— 第一版给功法 tab 的字形和「N 部」各挂一次,夜主题实测三块 `rgb(163,70,64)`
- 判据进 `palette.spec` 两条,都做过故障注入:彩色底配 `text-paper` 即红、
  `.seal-face` 底色带透明度即红

**判据不能以「这一行有 `.seal-face`」为前提**:把类换回 `text-paper` 之后那一行就不进扫描了,
故障注入实测是绿的。改判「彩色底 + `text-paper`」才抓得住。

### 同类已确认安全,别重查

- `bg-ink` 墨块上的 `text-paper`(契约印、InkTabs 选中条):日 12.99 / 夜 12.71
- `.btn-seal`、`.world-seal`:夜主题用 `cinnabar-deep` 兜底,5.31:1

### 方法

**对比度这类问题必须把两套主题都算一遍**。`layout-check` 只跑一种配色,
`aria-check` 只查属性存在性,两者都测不出「颜色对了但读不清」。
算一次不高:token 都在 `style.css` 的两段里,写十行脚本就能把全部印面扫一遍。

## 二十二·补、只在特殊条件下出现的界面,没有一道门槛看得见(第 249 轮)

这一轮抓到三个缺陷,全在**同一类界面**上:它们只在特定时刻出现,
而所有界面自检(node scripts/layout-check、ui-smoke、aria-check、focus-check)都看不见。

| 缺陷 | 触发条件 | 谁该发现它、为什么没发现 |
| --- | --- | --- |
| 更新横幅被拉成 788px 遮罩,整页点不动 | SW 装上新版本 | `layout-check` 巡页时不会触发 SW 更新 |
| 同横幅两颗钮低于 28px(24.5 / 21.4px) | 同上 | 触控尺子按巡到的页面量,横幅不在其中 |
| 同横幅被 toast 整个盖住,「重新加载」点不到 | 同上 + 有提示在屏 | 两者层级 z-50 / z-70、位置都在顶部 56px 附近 |
| 功法满级时页脚「进 修」消失 | 功法练满 | 巡页夹具不带已习得功法,**一页都点不开功法弹窗** |

**同一个横幅一次翻出三条**,而且是叠加关系:先发现它铺满整屏(几何),
修完才看见两颗钮不够大(尺寸),再往下才注意到它跟 toast 抢位置(层级)。
单看模板哪一条都不显眼 —— 都是 `class` 里少一个词或多一个词。

第三个还多一层:它在 `plans` 第十一节被**明确记为「不是缺陷」**,理由是「满级时下面走悟道分支」。
记录本身就是那道免检通行证 —— 再有人看到同样的疑问,查到的是一句「已判定无问题」。

### 判据

**「这个界面的前置条件,巡页夹具能铺出来吗?」** 铺不出来就得写静态断言,
或者给它一条专门的探针。三条落点:

- `uiLayering.spec`:横幅外层必须 `items-start`(缺省 `stretch` 会拉满)、
  两颗钮的类名须过 28px(`!py-1.5` / `h-7 w-7`)
- `masteryMark.spec`:功法进修钮不得写 `v-if="upCost"`
- 共同的找法:搜 `v-if="<store 状态>"`,逐个问「巡页夹具会不会把它点亮」

### 顺带记一条 CSS 隐式依赖

`:focus-visible` 能压住 Tailwind 的 `outline-none`,**只因为它是写在 `@tailwind utilities` 后面的**
—— 两者特异性都是 0-1-0。这条依赖此前没有断言(`focus-check` 查的是焦点落在哪,不查描边可不可见),
已补 `focusRing.spec` 四条。

## 二十三·补一、判据被 HTML 属性里的 `>` 截断(第 250 轮)

Vue 模板里 `v-if="rounds > 5"`、`:disabled="x > 0"` 这类写法很常见。
而判据普遍用 `/<button\b[^>]*>/` 取开标签 —— 正则看到引号里的 `>` 就当标签结束,
**截断点之后的属性全部看不见**。

### 实测规模

全仓 289 个 `<button>` 里 **11 个被截断**。三条判据受影响:

| 判据 | 截断造成的后果 |
| --- | --- |
| `ariaState` 互斥选择钮 / 展开钮 | `:class`、`@click` 落在截断点后 → 整颗钮不被检查 |
| `disabledReason` 禁用钮拒因 | `title` / `aria-label` 落在截断点后 → 「有拒因」误判成「没拒因」 |
| `uiLayering` generic 命名 | `:aria-label` 落在截断点后 → 漏报 |

第三条是这轮新写的判据,**第一版就踩了同一个坑**:它用 `[^>]*>` 扫,
而 `v-if="props.item.level > 0"` 正好把它们切开,装备卡「+N」那处真实违规整轮没被扫到。
改成按引号配对扫之后才抓到。

### 判据

```ts
// 按引号配对往后走,遇到不在引号里的 > 才收尾
function openTags(text: string, tagName: string): { tag: string; index: number }[]
```

**顺带把起始下标一并返回**:报错行号仍按原来那样算,不必从标签文本里反推。

### 教训

写源码级判据时,**先问「我要找的那段文字,会不会已经被正则切掉了」**。
`[^>]*>` 这个写法看上去无害,实则在模板里到处漏。
与第二十三节「判据不能以被检查的东西为前提」是同一类:
判据看不见目标时**不会报错,只会静默放过**,这比误报更难发现。

## 二十三·补二、可访问名的三个层次(第 250~251 轮)

这一族问题分三层,每层都能单独「看起来没问题」:

| 层 | 判据 | 实测漏了多少 | 怎么发现 |
| --- | --- | --- | --- |
| 一 **有没有名字** | `aria-label` 存在 | 5 处挂在 `generic` 上,严格实现直接丢 | AX 树的 role 是 `generic` 而非 `image` |
| 二 **名字有没有主语** | 念出来听得懂吗 | 页签「购」「售」、战报速度「×2」 | 扫 AX 树里名字≤1 字或纯符号的控件 |
| 三 **名字与可见文本一致吗** | 语音控制念屏上的字能不能命中 | 4 处(含我自己刚修的两处) | 比对 `aria-label` 与元素的文本子节点 |

**第三层最容易在修第二层时引入**:把「购」的读屏名写成「买货」看着更清楚,
但语音控制用户念的是屏幕上那个「购」,于是点不中。WAI-ARIA 的规矩正是
「名字应包含可见文本」,所以正解是「购买」「出售」——以可见字开头、又补足了主语。

### 找法

```js
// 在真实 DOM 上比对,不要读源码(插值拼接的名字读源码看不出来)
const visible = [...el.childNodes].filter(n => n.nodeType === 3).map(n => n.textContent.trim()).join('')
label.includes(visible)  // false 即是违规
```

16 个路由全扫,修完为 0。

### 别误报的两类

- **名字比可见文本更全**是允许的(「分解(已装备)」、按钮写「强 化」名字写全)。
  判据只查「可见文本是否被名字包含」,不要求相等。
- **`aria-label` 覆盖子元素文字**时,子节点是元素不是文本节点,上面那段自然跳过,不会误报。

## 二十四、品阶色当文字用有两档读不清(第 248 轮,**未修,待拍板**)

对着真实渲染逐页量对比度(两套主题 × 14 个路由)时,翻出一处此前没人查过的地方:
**品阶色既是装饰(光环/边框/角章/底纹),也被直接当文字颜色用**(装备名、货架品名、角标数)。

装饰那一层没问题 —— 它只需要「分得开」,`palette.spec` 的 ΔE≥10 已经在管。
但文字那一层要求 4.5:1,九档里有两档过不去:

| 品阶 | 色值 | 日主题(纸面) | 夜主题 |
| --- | --- | --- | --- |
| 天品 | `#C9A227` | **2.11 ✗** | 6.80 ✓ |
| 仙品 | `#3E8E8B` | **3.36 ✗** | 4.26 ✗ |
| 玄品 | `#A85C3F` | 4.28 ✗ | **3.34 ✗** |
| 神品 | `--color-cinnabar` | 5.32 ✓ | **3.83 ✗** |
| 其余五档 | — | ✓ | ✓ |

### 为什么不能直接压暗

压到 4.5:1 需要亮度落在一个**空窗口**里:亮底要求 L≤0.153,暗底要求 L≥0.314,两者不相交。
（因为这两套主题各自都要过,而同一个色值不可能既够暗又够亮。）

分主题给不同色值可以,但那会撞 `palette.spec` 的 ΔE≥10 守卫:天品压到 `#7E6314` 后
与地品 `amber-ink` 的 ΔE 只剩 **8.3**,九档里这两档就糊在一起了 —— 正是第二十二节
花了两百轮才拉开的那件事。

### 三条可行路线(都要先拍板)

1. **文字压暗、装饰不动**:色板不碰,只给「当文字用」的地方另起一档(如 `qualityTextColor()`),
   日主题取压暗版、夜主题取提亮版。ΔE 只评装饰色,守卫不用改。改动面:6 处内联 `:style`。
2. **文字不靠颜色区分**:装备名/品名统一用墨色,品阶只由角章、角饰、光环承担 ——
   与第二十二节的「形制才是可数的线索」一脉相承,但会减弱「一眼看出是高品」的直觉。
3. **放宽这条线的判据**:承认品阶文字是「装饰性强调」,按 3:1(大字 AA)考核。
   风险:天品 2.11 仍不够,仙品 3.36 勉强,玄品夜主题 3.34 勉强 —— 只救得回两档。

**判断**:这是设计取舍,不是 bug 修复。九档色板与「品阶视觉差异化」是 193~204 轮 +
第 218 轮定过案的,改它要先回答「品阶色到底是标签还是正文」。本轮只记录,不动手。

### 复现

```bash
# 起 preview 后逐页扫:把 span/p/button 的 color 与逐层合成的底色算对比度
# 关键判据:日主题 paper(243 239 228)与夜间 card(51 49 46)两个底都要 ≥4.5
```

**注意**:`layout-check` 只跑一种配色,`aria-check` 只查属性存在性,
`palette.spec` 只查 token 之间的关系 —— 三者都不会把「token 用在文字上」这件事算一遍。
这一轮是第一次把「实际渲染出来的前景/背景对」整体量过。

## 二十五、cinnabar 走的是「强调档」的宽线,却承担了正文字号(第 252 轮,**已修**)

`palette.spec` 把颜色分成两档:

| 档 | 线 | 成员 |
| --- | --- | --- |
| STRONG | **4.5** | ink / ink-soft / ink-faint / violet-ink / azure / gold-ink / amber-ink / jade / indigo-ink |
| WEAK | **3.0** | cinnabar(唯一一个) |

WEAK 的注释写的是「标题/图标/大字的主场」。但实测(夜主题,16 个路由):

```
cinnabar 文本的字号分布:{9:6, 10:4, 11:22, 12:1, 13:4, 14:2, 15:1, 17:1, 18:1}
小于 18px 的:41 处 —— 拒因、待办标记、可点装饰、"第 4 级"、参详 →、双灵根……
```

而夜主题的 cinnabar 对纸只有 **3.83:1**。也就是说:**全站唯一一个走 3.0 宽线的颜色,
承载了 41 处正文字号**。同一屏上 ink-faint 那类小字守的是 4.5。

### 为什么不能直接改档

把 cinnabar 挪进 STRONG 会立刻红(3.83 < 4.5),得先提亮 token。
但**夜主题的 cinnabar 同时是印面底色**:提亮到 4.5:1 约需 `rgb(224,124,116)`,
而 `.btn-seal` 的奶油字在它上面从 5.31 跌到约 3.4 —— 按下葫芦起瓢。

必须拆成两个 token(一个给文字、一个给印面),那是色板重构,牵动
`.btn-seal` / `.seal-face` / 品阶光环 / 朱砂描边等全部使用点。

### 修法(第 253 轮落地)

第 252 轮记的是「要拆两个 token」。**实测不成立**:夜主题的印面早已改走
`cinnabar-deep`,`btn-seal` / `world-seal` / `seal-face` 三处都有覆盖,
剩下用 `cinnabar` 当底的只有无字装饰(进度条、呼吸点、角标小块)。

所以只提亮文字用的那枚:`201 85 78` → `228 122 112`。

- 夜主题 cinnabar 文本 44 处,最差 **4.52:1**(原 3.83),四张底全过
- 印面奶油字仍走 `cinnabar-deep`,**5.31:1 未变**
- `palette.spec`:cinnabar 从强调档(3.0)挪进正文档(4.5),并加一条
  「一个 token 不能按两套线考核」的判据

### 教训

**「要拆 token」这种结论,得先把使用点逐个查一遍再下。**
当时只看到「夜主题 cinnabar 既是文字又是印面底」就下了判断,
而实际上印面早就被 `cinnabar-deep` 接管了 —— 一个 grep 就能否掉。

## 二十四·补、同色淡底 + 同色文字,是一套注定过不了 AA 的写法(第 253 轮,**第 264 轮已清**)

> 第 264 轮的处理见本节末「清理结果」。下面保留当初的分析。



把一类写法整体扫一遍,而不是逐页看渲染:

```
bg-cinnabar/10 text-cinnabar     14 处
bg-jade/15     text-jade          8 处
bg-gold-ink/10 text-gold-ink      8 处
…共 19 组彩色同色淡底
```

按「淡底叠到三张底上、再用同色作字」逐组算,**17 组跌破 4.5:1**,最差
`bg-cinnabar/10 text-cinnabar`:日 4.22 / 夜 3.91。

### 为什么调 alpha 救不回来

底色与文字同源,叠上去只会把两者拉近。把 alpha 压到让对比度过线,
那层淡底本身也就不存在了 —— **数学上没有可用的 alpha**。

唯一能同时保住「有色块」与「读得清」的做法:**文字走主题墨色,色块只做底**。
品阶角章走的就是这条路(深墨字 + 品阶淡底),所以它一直是达标的。

### 实测 vs 推算

真实 DOM 上合成有效底色扫 16 路由 × 2 主题,得到 21 个不达标样式,
其中两条是量法误报:

- InkTabs 的 `text-paper` 落在**兄弟节点**的滑动墨块上 —— 祖先链里没有那一层,
  合成出来是 1.01。这类「背景在兄弟节点」的情况,自底向上合成一律算不准。
- `q-plaque` 的品阶色字带 `text-shadow` 辉光,是另一套问题(见第二十五节)。

### 「降透明度」是错觉

第 253 轮之后我先想到的修法是「把 alpha 降下来」,并一度下了「低档(5%/8%)安全、
只有 10% 以上跌破」的判断 —— **错的**。按三张真实底逐档重算:

```
           5%            10%           20%
cinnabar   L4.51/D4.19✗  L4.22/D3.91✗  L3.65/D3.34✗
jade       L4.24/D5.00✗  L3.99/D4.53✗  L3.51/D3.79✗
violet-ink L4.43/D4.31✗  L4.17/D4.00✗  L3.63/D3.38✗
gold-ink   L4.44/D5.00✗  L4.19/D4.60✗  L3.66/D3.79✗
azure      L4.40/D4.32✗  L4.14/D4.02✗  L3.62/D3.40✗
amber-ink  L4.30/D4.77✗  L4.06/D4.34✗  L3.55/D3.66✗
indigo-ink L5.29/D5.26    L4.94/D4.81    L4.30/D3.97✗   ← 唯一低档安全
```

**除 indigo-ink 外,六种彩色在 5% 就已经有一边跌破。** 原因很直白:
这些色对纸本来就只贴着 4.5 过线,再叠一层自己的淡底必然拉近。

### 量法坑(这次踩的)

中途写了个临时脚本自算,得出「20% 都安全」的反向结论。原因是脚本里的底集合写成了
`paper / paper-deep / paper-lifted(244 240 230)` —— **夜主题的 `paper-lifted` 是
`51 49 46`,而日主题才是 `244 240 230`**。夜主题卡片是最亮的那张,对比度最低;
漏掉它就必然算乐观。

真实 DOM 上核对:徽章的祖先链是 `card-ink` → `rgb(51,49,46)`,正是 `paper-lifted`。

### 本轮做了什么

立**棘轮**:登记 19 组彩色同色淡底的出现次数,新增一行就红;
另两条判据证明「这类组合确实过不了 AA」与「降 alpha 救不了」,
后者留 `indigo-ink` 作反例。

存量 50 处(实测跌破)未清 —— 改法是把文字换成 `text-ink`/`text-ink-soft`、
色块留在底上,那是 50 处视觉调整,单独立项。

### 清理结果(第 264 轮)

把 19 组组合按「是否真的承载文字」重新分了一遍:

- **18 处确实压着文字**(宿敌、境地已迁、版本号、备、主、可升层、待悟道×2、主脉、
  强化已至上限、被动、神通、第 N 层、结契称谓、墙、相伴、静、门类方印×3)
  → 全部改成 `text-ink` + 同色描边,色块保留
- 其余是纯图标块(HomeView 的六个入口格、BuffDialog 的图标位)与装饰,不受此约束

## 二十六、大数回算吃掉半值进位(第 254 轮)

`formatGN` 对千位档用 `Math.round(toNum(g))`。而 `toNum` 是 `m × 10^e` 回算:

```
gn(999.5)  →  { m: 9.995, e: 2 }
toNum      →  9.995 × 100  =  999.4999999999999
Math.round →  999            ← 应为 1000
```

同一个函数里,`999.6` 给 `1000`、`1000.5` 给 `1,001`,唯独 `999.5` 给 `999`。
**半值进位时灵时不灵**,而差额、报价、奖励全走这条路。

实测 499.5 ~ 1500.5 逐个核对:**修复前 163 个半值被吃掉**,修复后 0。

### 修法

传入的本来就是 `number` 时,原值有完整精度,千位档直接用原值取整;
传入 `GNum` 的(来自存档)没有原值,只能按 `m × 10^e` 回算 —— 那是数据本来的精度,
不算这里的问题。`formatNum` 也不再先 `gn(n)`,那一步正是精度丢失的入口。

### 顺手踩到的两件事

- **档位判定不能跟着改**。一开始顺手把「档位按取整后的值判」也改了,
  `format.spec` 里既有断言 `formatGN(999.9) === '1000'`(不带千分位)立刻红。
  那是既定口径,不是缺陷。**改显示精度时,先看既有判据钉的是哪一条。**
- **注释里写了个 `²`**,`kaiFontCoverage.spec` 立刻报「子集缺字 1 个」。
  楷体子集不含上标数字,注释也算在内。

### 这一类怎么找

格式化函数的边界值,拿 `x.5` 系列去试最有效 —— 半值正好落在 `Math.round` 的刀口上,
浮点误差在这里被放大成可见的 1。`x.4`、`x.6` 反而是安全的。

## 二十七、首帧:没人量过的那 200 毫秒(第 255 轮)

所有界面自检都在**页面加载完之后**才开始量(`layout-check`、`ui-smoke`、`aria-check` 都是 `goto` 之后 `waitForTimeout`)。于是「首帧长什么样」这件事,一直没有任何判据看着。

实测:暗色主题的用户,前 **198ms** 里 `data-theme` 还没挂上,状态栏是亮色 `#F3EFE4` —— 一屏白底加一条亮状态栏,慢设备更久。

### 为什么一直没被发现

- 自检脚本一律等页面稳定才量
- 开发时热更新不会重走冷启动
- 只有「明确选过暗色」或「系统暗色」的人才会看到,而且只在打开的那一瞬

### 卡点:存档是加密的

主题存在 `settings` 分片里,而那一片是 AES 加密的 —— `index.html` 的内联脚本解不开。
解法是另存一个**只写 `light`/`dark` 的明文小键**(`yunyin.__theme`),与既有的
`yunyin.__live` 心跳同规:不含玩家数据,只是个渲染提示。

### 连带翻出的第二处

标记加上之后,`clearAllSave` 只清 `PERSISTED_STORES` 里的键,这个新键不在清单里。
实测:选过暗色 → 清档 → 重进,系统是亮色、新档也回到默认跟随系统,
**首帧却仍按残留的暗色渲染**,直到 App 挂载才翻回来。新角色顶着上一位的主题闪一下。

### 分层上的小摩擦

`utils/storage.ts` 要清这个键,而键名定义在 `core/theme.ts` —— 但分层判据规定
**utils 不许引 core**。最后在 storage 里重抄一份字面量,由 `palette.spec` 钉住两处一致。
这类「一个字符串要跨三层」的常量,分层规则下只能靠判据守住。

### 这一类怎么找

问「**有没有哪个时刻,没有任何自检在看着这个页面**」。首帧、页面卸载、切标签页、
关窗前来不及落盘 —— 都在这条线外。

## 二十八、加一个键,改坏了一个判定(第 256 轮)

上一轮为修首帧主题,加了一个明文小键 `yunyin.__theme`。它本身没问题 —— 问题是**它长得像存档**。

「两页同开」的判定原先写的是:

```js
if (e.key.startsWith('yunyin.') && !e.key.startsWith('yunyin.corrupt.')) setOtherTab(true)
```

`yunyin.__theme` 以 `yunyin.` 开头,于是被当成「另一页在写档」。

### 后果比误报一次更糟

`otherTab` 只在**心跳超时**时复位(`setOtherTab(false)` 全仓只有一处,在 `watchOtherTabSave(false)` 里)。
所以主题键把它置真之后,它就那么挂着;等玩家真开两页时,那条「存档已在另一页打开」
因为 `setOtherTab` 有去重,**反而一声不响**。

一次假警报,换掉了将来那次真警报。

### 修法

用 `PERSISTED_STORES` 派生一个键集合,只认真正的分片:

```js
const SAVE_SLICE_KEYS = new Set(PERSISTED_STORES.map(id => SAVE_PREFIX + id))
```

前缀匹配天生会长出新成员;要让「新加的键不算进度」这件事成立,只能反过来**枚举**。

### 教训

**给存档命名空间加键时,先搜一遍谁在按前缀认它。**
`startsWith(前缀)` 这种写法在加键的那一刻就悄悄失效了,而且失效方向是「多认」,
不会有任何报错 —— 只会在很久以后表现为「该报的没报」。

## 二十九、一天里只有几个小时能测出这个 bug(第 257 轮)

导出存档的文件名写着:

```js
`yunyin-xiuxian-${new Date().toISOString().slice(0, 10)}.save`
```

`toISOString()` 是 **UTC 日**。东八区本地 08:00 之前,UTC 还停在前一天 ——
实测本地 11 月 3 日 06:00 导出的文件叫 `yunyin-xiuxian-2026-11-02.save`。

全站其他日期(今日任务重置、修习日号)一律走本地日,只有这一处漏了。

### 判据本身也被时间骗了

补了一条校验本地日的判据,**用真实时间跑,故障注入没红**。
原因很简单:一天里绝大多数时间,本地日与 UTC 日是**同一天**。
写错的实现照样通过 —— 只有本地 00:00~08:00(东八区)那几个小时才暴露。

改成伪造时刻:

```ts
vi.setSystemTime(new Date(2027, 0, 2, 0, 30))   // 本地 1 月 2 日 00:30,UTC 还是 1 月 1 日
```

这才有鉴别力,故障注入立刻就红了。

### 更深一层

补判据时先问「**这个 bug 在一天里/一年里什么时候才显现**」。
时区、夏令时、月末、闰年、跨年 —— 这些位置拿「此刻」去测,大概率测的是安全的那一段。

顺带:既有那条判据只验格式 `/\d{4}-\d{2}-\d{2}/`,不验时区,所以它守着这个函数
却一直没抓到这处。**格式对不等于内容对。**

## 三十、等号遇到未来的值,两个方向各错一边(第 258 轮)

三道每日闸门写的都是等号:

```js
player.lastCaveEventDay === today          // 洞府巡游
wudaoExchange.gameDay === day              // 悟道兑换
endgame.dailyDoneDay === daily.day         // 天道挑战
```

而 `sanitize` 只验「是不是有限数、是不是非负」——**未来的日号一路放行**。
实测注入 `today + 10000`,三个字段原样留下。

### 两个方向各错一边

| 字段 | 未来的值让等号恒假,于是 |
| --- | --- |
| `lastCaveEventDay` | 「今日已抽」永不成立 → 每日巡游**永久停摆** |
| `wudaoExchange.gameDay` | 「今日已兑」永不成立 → 每日兑换**永久停摆** |
| `dailyDoneDay` | 「今日已挑战」永不成立 → **每天都能重复领赏** |

前两个是「玩法没了」,第三个是「能刷」。都不会报错,玩家只会觉得「这个每日怎么没了」。

### 为什么这类容易漏

`lastUpdateAt`、`expiresAt` 这类**时刻**字段,未来的值是正常的(未来才到期);
而**日记号**不是时刻,它是「哪一天做过」的标记,未来的值没有任何合法含义。
两类字段在 sanitize 里长得一样(都是 number),判据也就一抹带过。

### 判据

按「今日未做」处理 —— 归零(`dailyDoneDay` 归 `null`),与坏档该有的行为一致。
健康的「等于今天」原样保留,这一条也在 spec 里验了。

### 顺带

`mansionRedirect` 与 `astronomy` 的两处 `gameDay !== day → return null` 是**安全方向**
(不相等即失效),不会永久停摆,不必改。**同样是等号,方向的后果不同** ——
判断要不要修,得看错了之后是「恒真」还是「恒假」。

## 三十三、按「码元」截断,等于按半个字截断(第 262 轮)

三处玩家可输入的短字符串都写 `slice(0, N)`:

```js
name.value.trim().slice(0, NAME_MAX_LENGTH)   // 道号,8
l.name.trim().slice(0, NAME_MAX_LENGTH)       // 构筑名
it.note.slice(0, 4)                           // 装备标记,4
```

`slice` 数的是 **UTF-16 码元**。emoji 占两个码元,于是在第 8 位上恰好被劈开:

```
'一二三四五六七' + '\u{1F600}'  →  slice(0, 8)  →  '一二三四五六七\ud83d'
                                                    isWellFormed() === false
```

### 为什么它一直没被发现

这种串**能正常存进存档、正常读回** —— `JSON.stringify` 会把它转义成 `\ud83d`,
`JSON.parse` 又还原回来,往返完全一致。所以存档层的判据全都看不见它。

它只在**渲染**时表现为一个乱码方块,而且要求名字里恰好有 emoji 且恰好卡在第 8 位上。

### 修法

新增 `truncateCodePoints(s, max)`:先 `Array.from` 拆成码点,再截。

三处入口都换掉。上限仍是 8 —— 心智模型从「8 个码元」改成「8 个字符」,
后者才是玩家理解的「8 个字」。

### 一个连带发现

注释和判据里如果写真实 emoji,`kaiFontCoverage.spec` 会立刻报「子集缺字」——
楷体子集不含 emoji 字形,而那条判据把注释里的字也算进去。

所以这类字符在**注释里也要写成转义**。与上一轮注释里写 `²` 是同一个坑。

### 这一类怎么找

问「**这个限制数的是什么单位**」。`slice` / `length` / `maxlength` 数的是码元,
而「字数」「字符数」在玩家脑子里是字符 —— 两者只对 BMP 字符一致。
凡是对玩家输入做长度限制的地方,都要问一遍。

## 三十六、QA 夹具自己也坏了,而且坏了很久(第 268 轮)

`scripts/lib/saveFixture.mjs` 给五个 QA 脚本(`ui-smoke` / `aria-check` / `focus-check` /
`multitab-check` / `perf-profile`)提供起始存档。里面那件装备有两处错:

```js
{ uid: "smoke_a", templateId: "a_hufu", … }   // a_hufu 不存在
equipped: { weapon: "smoke_w", armor: "smoke_a" }   // armor 不是合法槽位
```

- 真实模板前缀是 `w_`(武器)/ `h_`(头冠)/ `b_`(衣袍)/ …,**没有 `a_`**
- `EquipSlot` 是 `weapon|head|body|wrist|belt|boots|necklace|ring|artifact|talisman`,**没有 `armor`**

后果:

| 现象 | 原因 |
| --- | --- |
| 藏品区显示一个「?」占位 | 模板查不到,`template?.name ?? '?'` 走了兜底 |
| 头冠那格一直是「未装备」 | `armor` 键被忽略,那件装备根本没穿上 |

### 为什么五个脚本都没发现

它们**不会报这个** —— 都不检查「装备栏是不是空的」,
`ui-smoke` 只查运行时异常,`aria-check` 只查属性存在性。
**起始状态本身就是错的,而判据只核对「相对它自己的变化」。**

### 怎么发现的

**看截图。** 前面二十几轮我一直在读代码和跑脚本,这一轮把页面截下来直接看,
第一眼就撞见那个「?」。

### 教训

**夹具的错最容易被判据吞掉** —— 它是所有检查的基准,而基准本身没人验。

### 补上的判据(第 269 轮)

`ui-smoke` 在入座之后、开始点按钮之前,先验五项**能一眼看见**的:

```
灵石余额 9.038兆 · 器灵尘 500 · 已装备的武器「雾隐长枪」· 已装备的头冠「桃木簪」· 2 世
```

任一项找不到就记一条 `where: 'fixture'` 的错,和运行时异常同等待遇。

**故意不写成全量比对**:夹具改了判据要跟着改,写得太细会变成第二个假基准。
五项覆盖了资源、装备、轮回三个不同 store,任何一处写坏都会露头。

## 四十一、过场层补验:动画本身与 reduce-motion(第 275 轮)

上一轮结论是「那 2.5 秒是 `WarpPortal` 过场动画,`innerText` 读不到」。
本轮把它补验完整:**截图看它长什么样**,以及**降动效两档是否真的停住**。

### 动画本身

截图确认:金色光晕居中、放射线自中心铺开、下方「云深不知处 / 仙路自此始」。
画面完整,不是空白 —— 上一轮「测不到 ≠ 不存在」的判断成立。

### reduce-motion:两档都停住了

`WarpPortal` 内部有多条 `animation: … infinite`(星点流动、光环脉冲、射线展开),
组件自己**没有**写 `prefers-reduced-motion` 分支。看着像漏了。

但 `style.css` 有全局兜底,两档各一段:

```css
@media (prefers-reduced-motion: reduce) { *, *::before, *::after { animation-duration: .01ms !important; … } }
.reduce-motion *                        { … 同上 … }
```

实测(过场播放中逐个读 `getComputedStyle`):

| 档位 | 仍在动的元素 |
| --- | --- |
| 系统 `prefers-reduced-motion: reduce` | **0** |
| 设置项 `.reduce-motion` | **0** |

**全局兜底 + `!important` + 带伪元素**是这套写法扎实的原因 ——
组件不必各写一遍,也就不会漏。这条以后再看到「组件没写 reduce-motion」不用查了,
先看全局那段。

## 四十五、尸体还能追着打一下,把血吸回来(第 283 轮)

并行派了两个子代理审核心模块,其中一个留下了几个探针,其中 `zzResurrectFinal` 那条最有意思。

### 缺陷

反击是「对方打完那一下顺带还手」,它**可能当场把出手方打死**。而追击、震摄这些
后续节拍仍挂在**出手方**身上,代码只查了「对手还活着没有」:

```ts
if (!isZero(target.hp) && rng.chance(...comboRate)) { /* 追击 */ }
```

**没查自己。** 实测(攻击 100 / 吸血 5% / 连击 100%,对手攻击 200 / 反击 100%):

```
3: php=0.0000  【敌】使出反击,击中你。      ← 玩家死了
4: php=0.0000  你使出追击,击中【敌】。      ← 尸体还在打
5: php=0.0030  【敌】轰然倒地,你胜了。      ← 吸血把血吸回来,判胜
```

### 为什么这条几乎肯定该修

同一个 `strike()` 里,另外两处早有同样的检查:

```ts
strike(...玄罡反震...);
if (isZero(attacker.hp)) return      // ← 第 379 行,有
...
if (opts.skipFollowups) return
if (isZero(attacker.hp)) return      // ← 第 402 行,我补的
```

作者的意图是明确的「自身归零就收手」,**唯独反击到追击这一段漏了**。

### 连带影响:两条平衡基准变红

修完之后 `bun run test` 红了三条,全是**衡量的基准**,不是行为断言:

| 基准 | 原值 | 修后 | 为什么 |
| --- | --- | --- | --- |
| 最强构筑最弱场景 | ≤92% | 95% | 罡盾/反震在高爆发场景升上去了 |
| 手工世界可行流派数 | ≥3 | 2 | **反震流 60% → 20%** |
| 风险图谱覆盖率 | 全登记 | 缺 3 条 | 反震一系跨过破墙线,露出新结构 |

**反震流垮掉是有道理的**:它的核心收益本来就是「死了还能打、还能吸回来」。
修掉之后,那条路子没了。

### 处理

按「保留修复、重新校准基准」办:

- 阈值按新实测改,并**在注释里写清为什么变、以及别把它当放宽条件的借口**
- 风险图谱补登三个新结构,档次 `watch`(破墙率仍 0.8%,红线 1.5%)
- **反震流的数值补偿没做** —— 那是平衡调整,不该由一次 bug 修复顺手决定

### 补验:修复到底动了多少平衡(第 284 轮)

上一轮我按「保留修复、校准基准」办了,但那时**没有量过修复对常规战斗的影响**。
这轮补上:

| 场景 | 修复前 | 修复后 |
| --- | --- | --- |
| 势均力敌(攻防 100/100,血 1000/1000) | 89.0% | **89.0%** |
| 宽扫 21 组攻防血组合 | — | 11 组落在中间态(非全胜/全负) |

**常规战斗一点没变。** 修复只切掉「被反击打死那一瞬」的后续节拍 ——
它要求「反击真的把人打到 0」,而那在普通对局里本就少见。

所以先前那三条基准变红,不是战斗整体偏移,而是**反震流那条特定路子被掐掉了**:

```

```

它原本就靠「死了还能打一下吸回来」撑起三成胜率。这个数降得对。

## 四十四、首字母当散列用:三组天时共用同一个劫(第 282 轮)

劫型由「境界 × 今日天时」派生:

```ts
const seed = targetMajor * 31 + ((todayWeather().id.charCodeAt(0) - 96) * 7)
```

**`charCodeAt(0)` 只认首字母。** 14 个天时里三组首字母重合:

```
l: leiming / lingyu
s: shenhui / shenwei
x: xianjie / xianyu
```

实测(境界 5):同组两个天时算出的种子分别是 **239 / 239**、**288 / 288**、**323 / 323** —— 完全相同。
于是「按今日天时派生劫型」形同虚设:**换了个天时,劫型纹丝不动。**

### 修法

djb2 走完整 id,再 `% 509` 收成小整数。509 不是随手挑的 ——
把 14 个天时逐个试过,它在「零碰撞」与「劫型够不够多样」之间最平衡:

| 模数 | 14 个天时去重 | 实际 5 天时派生几种劫型 |
| --- | --- | --- |
| 97 | 13(**撞一组**) | 4 |
| 101 | 14 | 3 |
| 257 | 12(撞两组) | 4 |
| **509** | **14** | **4** |

实测结果:14 个天时零碰撞;真实 20 天里出现的劫型从 **2 种变成 4 种**。

### 一条写错又改对的判据

第一版判据**在 spec 里复刻了一遍 djb2 算法**再自测。结果故障注入时发现:
把实现改回 `charCodeAt(0)`,判据**依然全绿** —— 它测的是自己那份副本。

改法:把 `weatherSeed` 导出,判据直接调用实现里的函数。
再注入一次,两条当场红。

**判据不能复刻实现。** 复刻出来的是「两份一样的错」,而不是「一份对、一份错」。

### 顺带记一个数

14 个天时里,真实 20 天只会碰到 5 种(leiming / chiyang / yueshi / lingyu / qinghe),
**另外 9 种在这个样本里一次都没出现** —— 天时是加权的,清和占三成。这不是缺陷,
但说明只用「跑 20 天」去测天时相关逻辑,覆盖会窄。

## 三十九、重复代码:哪些该抽,哪些抽了更糟(第 273 轮)

上一轮把 `layout-check.mjs` 里抄了 23 遍的密钥抽成常量,这一轮顺手扫了全仓的重复。

按「同一行出现 ≥3 次」扫 `src/` 的 ts/vue:

| 重复 | 次数 | 判 |
| --- | --- | --- |
| `<div class="stagger-in space-y-4 px-4 pb-6 pt-4">` | 16 | 模板约定,不动 |
| `const rng = new RandomService(mulberry32(seed))` | 13 | 一行样板,抽了收益不抵 13 个文件的回归风险 |
| `if (!raw \|\| typeof raw !== 'object' \|\| Array.isArray(raw)) return null` | 9 | **不该抽**,见下 |
| `const build = detectBuild(player.finalStats.mods)` | 6 | 一行调用,不动 |

### 为什么那 9 处形状守卫不该抽

它们看起来一模一样,但**各自返回不同的类型**:灵根、秘境、节奏遥测、行囊……
抽成一个泛型 `asRecordOrNull<T>` 之后,调用点得写类型参数,
而该函数的职责也从一个具体判据变成「什么都判」——

**重复的判据不是重复的逻辑**。两处 `return null` 背后的类型无关,
抽走以后读代码的人还得跳一层才知道返回的是什么。

### 一条尺度

判断要不要抽,问:**抽掉之后,调用点是否还看得懂它在判什么?**
- 看得懂(密钥、前缀、加密函数)→ 抽
- 看不懂(形状守卫返回各自的类型)→ 不抽

## 三十八、又一批查稳的:异常回执 / 连点去重 / 数字边界(第 272 轮)

承接第 261、263 轮那两张表,这一轮补三组,同样**未找到可提交缺陷**。

| 方向 | 怎么验的 | 结论 |
| --- | --- | --- |
| `catch {}` 是否吞掉信息 | 全仓 grep,逐块看 | 6 处全部返回有意义的回执(「文件无法解析」「检索失败」、`return null` 由调用方判「文件无法读取」);**没有一处是空 catch** |
| 连点会不会重复执行 | 对「买下」`clickCount:3` | 只弹 1 条回执、无 NaN、无报错 —— 有去重 |
| 数字格式化边界 | 单位表逐档 + 千分位 | 万/亿/兆/京/垓/秭/穰 全部正确;999999 → `100万`、1e6 → `100万` 一档不错 |

游戏实际数值离 e307 还差十几个数量级,这一档永远不会被玩家看到,
但它保证了「再离谱的存档也不会印出 `Infinity`」。

## 三十七、非文本图形:没人量过的第二档对比度(第 270~271 轮)

WCAG 有两条线:**文字 4.5:1**,**图形/图标 3:1**(1.4.11)。

`palette.spec` 只守着第一条。于是「既不是文字、也不是布局」的元素,
一直是两套判据的缝。

### 两处,都在界域志

| 元素 | 原值 | 日 | 夜 |
| --- | --- | --- | --- |
| 状态点「未至」 | `bg-ink-faint/40` | **1.74** | **2.01** |
| 等级金点 | `bg-gold-ink/60` | **2.46** | **2.93** |

两处都连 3:1 都不到。修法分别是 75 与 80(日 3.18/3.54,夜 3.53/4.06)。

### 顺手把这一档扫干净了

写了个按「小面积色块」扫的脚本(圆点、进度条填充,尺寸 ≤40px),16 个路由 × 两套主题:

```

修后:0 处
```

### 一个反复踩的量法坑

算对比度时**先量清真实的底**。我第一次把卡片底当成 `rgb(51,49,46)`(夜),
算出「日主题即使不透明也只有 2.16」的荒谬结论 —— 而日主题的卡片其实是
`rgb(244,240,230)`,差得远。

**从 DOM 里读祖先链的真实背景色,别凭印象填。**

### 判据

`palette.spec` 补一条:非文本图形守 3:1,并额外断言**不得为了对比度把三态改成同一个墨色** ——
那是这类修复最容易走偏的方向(对比度达标了,状态却分不出了)。

### 规模

8 个路由逐页量「被提示条覆盖的可点元素」:

| 路由 | 被覆盖 |
| --- | --- |
| `/inventory` | **12** |
| 其余 7 个 | 0 |

背包格密集排列,提示条浮在 `top-12`,一次连弹五条时正好压住上面两排格子。

### 为什么这一条难修

`pointer-events-auto` 是**必要的** —— 提示条靠点击关闭,全透明穿透就关不掉了。
所以不能简单去掉。

可选的修法各有代价:

- 缩短提示时长 / 减少条数 → 治标,且改动状态播报的手感
- 把提示挪到不压内容的位置 → 屏内没有那样的地方(顶部是内容,底部是导航)
- 只让「关闭热区」吃事件(比如右侧的一个 × ),提示本体穿透 → 改交互,得先定
- 让提示在鼠标按下时穿透(`pointer-events` 按 `:hover` 切换)→ 逻辑绕,易出 bug

**这是交互取舍,不是纯缺陷。**记在这里等拍板,没有擅自改。
